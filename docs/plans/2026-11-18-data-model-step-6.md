# Data model step 6 implementation plan

> **For Claude:** REQUIRED SUB-SKILL: Use superpowers:executing-plans (or subagent-driven-development in this session) to implement this plan task-by-task.

**Goal:** The legacy tables and columns go. After this step a Season Pass is a job and nothing else, a job has no typed status, price or kind, money is only payment rows and line items, history is only `event`, and the people who work here are only `person`. The model in `docs/plans/2026-11-16-data-model-design.md` is closed, except `area` (and the Areas, Fall order, Spring order and Season windows settings), whose replacement (Routes and Seasons, designed in PR #46) waits for Hannah's answers and is untouched here.

**Architecture:** Expand, then contract, in two pushes, because a pushed branch migrates the production database at once and the live code (`main`) must never meet a column it still reads missing. **Push A** (branch `step-6-legacy`, this plan's tasks 6.1 to 6.5) adds the new columns, backfills, relaxes the constraints the old code needed, and moves every reader and writer off the legacy tables and columns; `src/db/schema.ts` stops declaring them, but no `DROP` has run, so A's code runs on the database before and after. **Push B** (branch `step-6-drops`, task 6.6, pushed only after A is merged and live) is the one migration with every `DROP`, guarded by `DO` blocks that raise (and so abort the whole migration) if a verification fails. The reconciliation queries are in both PR bodies. Both are branched from `main` at `e75b7c3` (B from A's tip, so it carries A's commits until A merges).

**Tech Stack:** as step 3 (`docs/plans/2026-11-17-data-model-step-3.md` header): Next.js 16 App Router, Drizzle on Neon (migrations generated by `npx drizzle-kit generate --name <name>`, then edited by hand for the backfill; applied by `scripts/db-migrate-on-build.mjs`, which also runs `scripts/db-seed.ts` when `SEED_ADMINS` is set), vitest with pglite (`src/db/test-db.ts`, `src/api/test-helpers.ts`, every test database applies every migration and the seed), zod handlers in `src/api/v1/*` registered in `src/api/v1/index.ts` with a route file under `src/app/api/v1/`, Storybook with axe, the design gate in `npm run lint`.

Design: `docs/plans/2026-11-16-data-model-design.md` ("What goes", "Lifecycles", "The Season Pass on this model"; build order 6). Then `docs/DATA_MODEL.md`, `docs/DESIGN.md`, `docs/UX_WRITING.md`, and the step 3, 4 and 5 plans for the format and their "left for step 6" lists.

**Rules that hold for every task**

- A pushed branch migrates and seeds the production database at once (Preview and Production share `DATABASE_URL`). The branch is pushed only when the whole step is done, and a migration is never edited after its commit is pushed.
- Every backfill is idempotent (`where <new column> is null`) and every seed insert is safe on a migrated database with real rows (`src/db/seed.ts` upserts by id and never overwrites a column the office may have edited).
- Old columns stop being the source of truth but keep being written where a write is cheap, so a rollback of the code (not the schema) still works for one deploy. They are listed in `docs/DATA_MODEL.md` as "legacy until step 6".
- Commit messages are one plain sentence ending with the line `Co-Authored-By: Claude Fable 5.1 <noreply@anthropic.com>`; `npx tsc --noEmit` and `npx vitest run --project unit` before every commit; new handler tests follow `src/api/v1/trucks/handlers.test.ts` (`apiDb()`, `ctxFor(db, adminKey)`). Words on screen: sentence case, no em dashes, the words in `docs/UX_WRITING.md`.
- Implementers never touch `drizzle/` except in the task that generates that task's migration, and never push.
- Step 5 additions: every query on `event` carries `organization_id`; the words "proposed" and "approve" appear nowhere; "failed" never appears on screen (say "didn't go through"); nothing is ever deleted from `event`, except the hourly purge of an unpaid pending pass's own rows (decision 9).
- Step 6 additions: a `DROP` is irreversible, so every drop is preceded in this step by a backfill and a guard that raises when the backfill is not complete; no `DROP` runs in push A; nothing is ever deleted in the model (records are cancelled or inactive; the only deletes are the hourly purge of an unpaid pending pass and the cache rows of the Jobber feed); the words "request", "proposed" and "approve" never appear on a screen or in a commit message (the old `quote_request` is named only in code, migrations and docs); no secret is read or printed, no migration is applied to the real database by an implementer, and no implementer touches Jobber or another project; every field touched keeps its row in `docs/DATA_MODEL.md` in the same commit (rows for dropped columns are deleted, and the row of what replaced them says so); files stay under 300 lines for admin and block files.

**Decisions made here (Hannah can reverse any of them)**

1. **The pass id becomes the job id.** `passes.*` keeps its names and routes as an alias API for one season, but `PassOut.id`, `VisitOut.passId` (the job's id when the job is a Season Pass, else null), `JobOut.passId`, the `pass.bought` and `pass.cancelled` and `charge.*` webhook payloads, new Stripe metadata `passId`, new queue keys and payloads, new `admin_alert` keys and the new signed links all carry the job id. `job.legacy_pass_id` (text, unique where set, backfilled from `season_pass.id`) keeps every old id working: one helper `resolvePassJob(db, organizationId, id)` (`src/lib/pass/server/resolve.ts`) finds the job whose `id` or `legacy_pass_id` is the given id and `season` is not null, and every entry point that can still receive an old id calls it: `passes.get` and every `passes.{id}.*` handler, `visits.list?passId=`, the `own-pass` guard in `src/api/core/call.ts` (compare the resolved job ids), `PublicPrincipal.passId` and `renewPassId`, `/api/pass-image/[passId]` (the HMAC is verified against the id string exactly as it arrived, then resolved), `/season-pass/checkout?renew=` (`renewal.ts`), the card-update and setup sessions' metadata read by `webhook.ts` and `applyCardUpdate`, `organizationOfEvent`, the `pass-onboard` and `pass-cancel` queue handlers, `alerts.dismiss`, and `/admin/passes?pass=`. `admin_alert.key` values that are an old pass id (or start with it and an `@`), and `message_log.key` of kinds `purchase-confirmation` and `cancelled`, are rewritten to the job id by the migration so a dismissal or a once-only send is not lost. `visit.pass_id`, `charge.pass_id`, `admin_alert.pass_id` and `pass_change.pass_id` stop being read or written in push A (the visit, the payment and the alert have `job_id`; `admin_alert` gains a nullable `job_id` backfilled from the pass), `season_pass` stops being read or written, and `src/lib/pass/facts.ts` is the only source of pass status, inspection and preferences; push B drops them. `syncPassJob` and `syncVisitAmount` are deleted. `visit_pass_kind_unique` becomes `visit_job_pass_kind_unique`, a partial unique index on (`job_id`, `kind`) where `kind in ('turn-on', 'inspection', 'blowout')`: Postgres cannot read `job.season` in an index predicate, and only a Season Pass job has two or three of those visits, so `visits.create` onto an existing job refuses a second visit of one of those kinds ("This job already has a turn-on visit"); the migration creates it after a guard that raises if two visits of one such kind already share a job. Deviation from the brief ("where the job is a pass"), forced by what an index can say.
2. **A job has no typed status.** `job.status`, `job.price` and `job.kind` stop being read or written in push A and are dropped in push B. A job's kind is derived (`jobKindOf`, `src/lib/jobs/kind.ts`): a job with `season` is a pass; otherwise the service kind of its first live line (`line_item.service_id` to `service.kind`), else its first visit's kind, mapped as `visits.create` mapped it (repair to repair, install to install, anything else to other); every query that asked "is it a pass" asks `season is not null`. `job.kind` is relaxed to nullable in migration 0021 so push A's inserts, which no longer write it, work. The stage words come from facts: Cancelled (`cancelled_at`, every line cancelled, or no live visit), Done (every live visit done), then for a job that is not a pass **Quoted** (`quote_sent_on` set, `quote_accepted_on` and `sold_on` empty) and **Needs a quote** (`sold_on` empty and no quote sent, or every line unpriced as today), else Open. A Season Pass is **pending** while `sold_on` is empty (checkout started, card not yet saved) and `cancelled_at` is empty; `markPassActive` sets `sold_on` to today in Denver with one atomic `update ... where sold_on is null returning`, so a page and a webhook racing to activate the same pass produce one winner and one `job.sold` event (the step 5 review's open race). Migration 0021 adds `quote_sent_on`, `quote_accepted_on` and `sold_on` (all Mountain calendar days, `day`), so step 7 adds no migration; `sold_on` is backfilled from the Denver day of `created_at` for every existing job **except** a job whose `status` is `pending`, which is not sold yet and stays empty (one deviation from "every existing job", needed so pending is still a fact). `jobs.create`, `visits.create` (office), `passes.sell` and `renewPass` set `sold_on` today; the old pass checkout leaves it empty until activation. The Jobs grid's Sold cell reads `sold_on` ("Not sold yet" when empty).
3. **Money columns on the visit go.** `visit.charged_at`, `visit.stripe_payment_intent_id` and `visit.amount` stop being read or written and are dropped in push B. The price of a visit is `jobTotal` of its own non-cancelled lines (with tax, decision 4); a visit with no line costs 0. The card-on-file charge charges that, not a column. Migration 0021 first writes the missing rows, so nothing is lost: a line `line_<visit id>` for every visit with `amount > 0` that has no line (priced `amount`, named from its kind with `LINE_NAMES`'s words), and a succeeded payment row `ch_legacy_<visit id>` (method `card_on_file`, amount the visit's amount, `paid_on` the Denver day of `charged_at`, the visit's job and customer, the next free attempt, the payment intent only when no other row has it) for every visit with `charged_at` set that has no succeeded non-refund payment on its job. The push B guard raises if any visit with `charged_at` still has no succeeded payment on its job. `visits.recordPayment` is removed from the registry and its route (callers use `payments.record`); `metrics.invoicesOverdue` reads our `invoice` table (open, due before today in Denver); the five `jobber_*` mirror tables and `mirror.upsert` stay (marked temporary in `DATA_MODEL.md`) until the exit, read only by the mirror screens, the customers `next`, the month totals and the calendar feed's busy blocks. API outputs keep an alias for a season, derived and not stored: `VisitOut.chargedAt` (the time of the newest succeeded payment when the visit is paid in full, else null, so the Jobber routine that reads it keeps working), `VisitOut.amount`, `JobOut.price` (the job total, null while it is 0), `JobOut.kind` (derived), `VisitOut.truckId` and `truckName` (the person's id and name), `VisitOut.notes` and `JobOut.notes` (the text of the newest `note` event about it, from the events already loaded).
4. **Sales tax folds into the job total.** Tax is per line and rounded to the dollar per line: `lineTax(line, rule) = round(quantity * unitPrice * percent / 100)` for a taxable, uncancelled line while `settings.billing.collectsSalesTax` is on, else 0; `jobTax` is the sum of the lines' tax, a visit's tax the sum of its own lines' tax (a line with no visit counts for the job only), so a job's tax always equals its visits' tax plus its visit-less lines' tax and a bill built from the same function always equals what the job owes. `jobTotal(lines, rule)` includes tax and `jobSubtotal(lines)` is what it was; `TaxRule` is `{ collectsSalesTax, salesTaxPercent }` (what `billingOf` returns). Every money word (`jobOwed`, `jobMoney`, `visitMoney`, `isPaid`, `allocateJobPayments`, `visitBalance`, `credit`), the card-on-file charge, `sendBill` (`amount` stays the lines' subtotal, `tax` is `jobTax` over the billed lines, `total` the two; "Payments received" credits stay), `startBillPayment` (the gates compare against the job's owed with tax, which now equals the bill's total) and the receipt read the same function. The job panel, the invoice email and the receipt show one "Tax" line only when it is above zero. `invoiceTax` is replaced by `jobTax` (per-line rounding differs from step 4's subtotal rounding by at most a dollar a line; nothing was ever billed with tax, the switch has been off). The Season Pass checkout and the pass page stay untaxed this step (their lines are not taxable) and say so in a comment. With this the Billing switch is safe to turn on; the PR body says so.
5. **Trucks, bookings, requests and admin users go.** Nothing reads or writes `truck`, `visit.truck_id`, `jobber_visit.truck_id`, `person.legacy_truck_id`, `booking`, `visit.booking_id`, `quote_request`, `admin_user` or `pass_change` after push A; push B drops them. `trucks.*` handlers, routes, OpenAPI and MCP entries are removed (the Jobber routine in `docs/jobber-routine.md` must switch to `people.*` and `personId`; the doc and the PR body say so); an input `truckId` on `visits.*`, `schedule.week` and the checkout's chosen days still resolves (`resolvePersonId`: the id, else `person_<id>`, the way migration 0010 made person ids) for one season; `person.legacy_truck_id` goes, the nightly feed's old busy rows (`feed:<truckId>:<uid>`) are mapped to a person by the key inside their id, and the person's first feed sync deletes them as today. `VisitFacts.crew` and the `{truck}` placeholder are removed (a stored `crew` key in queued messages is ignored by the renderer; a settings template that still says `{truck}` is left as written by `fillMessage`); the Messages tab's sample and the default day-before template use `{who}`. `bookings.cancel` stays as an alias over a job cancel and `bookings.create` stays unimplemented; `VisitOut.bookingId` goes. Migration 0021 first makes a job `job_<booking id>` for any booking that has none (none expected: migration 0008 made them all) and one job per `quote_request` row: the customer, the property on the row or the customer's newest, else a new one with the address "Address needed" in Erie (the notes carry the real words), one unpriced line from the service (the service's name, `description` the notes, `taxable` from the service), `sold_on` and `quote_sent_on` empty, source `site`, id `job_qr_<id>`, status `quoted` rows get `quote_sent_on` the day of `updated_at`, `archived` rows `cancelled_at` of `updated_at`, one `job.requested` event (`evt_qr_<id>`, who `system`, `at` the row's `created_at`). The website form (`src/app/api/contact/route.ts`) keeps sending its email first and then, best effort (a database error never loses the email or the visitor's confirmation), writes the same job through `jobs.create` with `needsQuote: true` as a system context; `quoteRequests.*` is replaced by `jobs.create` (scope write, `needsQuote` makes the sold date empty and the line unpriced) and the `request.received` outbound name stays, emitted from it. `admin_user`: sign-in has read `person` since step 1; `seed.ts` stops inserting `admin_user` and `truck`, and `seedPeople` takes admins from `SEED_ADMINS` directly. `pass_change`: `recordChange` takes `jobId` (not `passId`), writes only the event, and migration 0020's copy of every row is checked by the push B guard.
6. **One yard shape, one card helper.** `YardOut`, `Yard` and `ApiYard` become one exported type `Yard` in `src/lib/admin/types.ts` with its zod twin `YardOut` generated from the same field list in `src/api/v1/visits/schemas.ts` (a type test keeps them equal); `passHasCard` is deleted, callers use `customerHasCard`.
7. **Notes columns.** `visit.notes` and `job.notes` stop being read or written (the story is the events) and are dropped in push B; migration 0021 re-runs 0020's note backfill for rows typed since (one `note` event per non-blank value with no `note` event of the same text about that record, id `evt_note2_<record>_<id>`). `property.notes` stays: it is the standing fact about the yard.

**The backfills (appended in this order, each idempotent)**

2. `update job set sold_on = (created_at at time zone 'America/Denver')::date where sold_on is null and status <> 'pending'`.
3. `update admin_alert a set job_id = sp.job_id from season_pass sp where sp.id = a.pass_id and a.job_id is null`; then rewrite keys: `update admin_alert a set key = j.id || substr(a.key, length(j.legacy_pass_id) + 1) from job j where j.legacy_pass_id is not null and (a.key = j.legacy_pass_id or a.key like j.legacy_pass_id || '@%') and a.organization_id = j.organization_id and not exists (select 1 from admin_alert b where b.organization_id = a.organization_id and b.kind = a.kind and b.key = j.id || substr(a.key, length(j.legacy_pass_id) + 1))`; the same for `message_log.key` where kind is `purchase-confirmation` or `cancelled` (the unique is (kind, customer_id, key)).
4. Straggler lines, straggler payments (decision 3), straggler jobs for bookings, jobs and lines and events for quote requests (decision 5), straggler note events (decision 7), each with the exact conditions in the decision text and `on conflict (id) do nothing` or `where not exists`.

Guard then index: a `DO` block that raises `legacy_expand: two visits of one pass kind share a job` if `select 1 from visit where kind in (...) group by job_id, kind having count(*) > 1` returns a row, then the unique index from the schema (placed after the guard by hand if the generator puts it earlier).

**The reconciliation queries (for the PR bodies; run by the parent against production, never by an implementer)**

```sql
-- every pass has its legacy id on a job
select count(*) from season_pass sp left join job j on j.legacy_pass_id = sp.id where j.id is null;                     -- 0
-- every visit that was charged has a succeeded payment on its job
select count(*) from visit v where v.charged_at is not null and not exists
  (select 1 from charge c where c.job_id = v.job_id and c.status = 'succeeded' and c.amount > 0);                        -- 0
-- every priced visit has a line
select count(*) from visit v where v.amount > 0 and not exists (select 1 from line_item l where l.visit_id = v.id);      -- 0
-- every booking and quote request is a job
select count(*) from booking b where not exists (select 1 from job where id = 'job_' || b.id);                           -- 0
select count(*) from quote_request q where not exists (select 1 from job where id = 'job_qr_' || q.id);                 -- 0
-- every admin user is a person
select count(*) from admin_user a where not exists (select 1 from person p where lower(p.email) = lower(a.email));      -- 0
-- every pass_change row has its event
select count(*) from pass_change pc where not exists (select 1 from event e where e.id = 'evt_pc_' || pc.id)
  and not exists (select 1 from event e where e.organization_id = pc.organization_id and e.customer_id = pc.customer_id
                  and e.at between pc.at - interval '5 seconds' and pc.at + interval '5 seconds');                       -- 0
-- every sold job has its sold day; only pending passes lack one
select count(*) from job where sold_on is null and status <> 'pending' and source <> 'site';                             -- 0 (quote jobs are site and empty on purpose)
-- no dangling references
select count(*) from event where organization_id is null;                                                                -- 0
```
