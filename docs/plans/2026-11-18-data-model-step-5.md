# Data model step 5 implementation plan

> **For Claude:** REQUIRED SUB-SKILL: Use superpowers:executing-plans (or subagent-driven-development in this session) to implement this plan task-by-task.

**Goal:** Everything that happens is one `event` row with a name on it, about a customer, property, job, visit, payment or invoice, and a note is an event of kind `note`. A customer's, job's or visit's story reads in one list, newest first: "Nov 17 · Ryan · Spring turn-on marked done, paid by Venmo". `pass_change` stops being the place history goes; step 6 drops it.

**Architecture:** One `event` table and one writer, `recordEvent` (`src/lib/events/record.ts`). The old writer `recordChange` becomes a call to it and still writes its `pass_change` alias row for one season; `emitEvent` (outbound webhooks) can record the same event when it is given the record it is about. One action writes exactly one event: where a site has both a `recordChange` and an `emitEvent` (a pass cancelled, a pass sold), the `recordChange` writes the event and the `emitEvent` does not. Settings changes stay in `settings_change`; messages stay in `message_log` (the timeline reads them, never copies them). `visit.notes` and `job.notes` keep being written as aliases of the newest note about that record. One PR, `step-5-events`, branched from `main` at `22c5386`.

**Tech Stack:** as step 3 (`docs/plans/2026-11-17-data-model-step-3.md` header): Next.js 16 App Router, Drizzle on Neon (migrations generated by `npx drizzle-kit generate --name <name>`, then edited by hand for the backfill; applied by `scripts/db-migrate-on-build.mjs`), vitest with pglite (`src/db/test-db.ts`, `src/api/test-helpers.ts`), zod handlers in `src/api/v1/*` registered in `src/api/v1/index.ts` with a route file under `src/app/api/v1/`, Storybook with axe, the design gate in `npm run lint`.

Design: `docs/plans/2026-11-16-data-model-design.md` (the records table's Event row: "about (customer, property, job, visit, payment, invoice), its id, kind, detail, who, when; belongs to the record it is about"; "Everything that happens is an event with a name on it"; "What goes": `pass_change` replaced by event; build order 5). **Decisions made here (Hannah can reverse any of them)**

1. **The table.** `event`: `id` (`evt_<uuid>`), `organization_id`, `about` (text: customer, property, job, visit, payment, invoice), `about_id`, `customer_id` (null only for an event with no customer), `job_id` and `visit_id` (nullable: the job and the visit the event belongs to when it has them; denormalized so a job's or a visit's story is one indexed query, like `customer_id`), `kind` (text, the vocabulary below), `detail` (jsonb, default `{}`), `who`, `at` (timestamptz, default now), `created_at`, `updated_at`. Indexes: (`organization_id`, `about`, `about_id`, `at`), (`organization_id`, `customer_id`, `at`), (`organization_id`, `job_id`, `at`), (`organization_id`, `visit_id`, `at`). No foreign keys on `about_id` (it points at six tables); `customer_id`, `job_id`, `visit_id` are plain text too, so a purge never trips on them. `job_id` and `visit_id` are added to the brief's column list on purpose.
2. **Who.** `who` is the signed-in person's email, or `customer` (a customer's own action on the pass page), or `system` (the scheduler, a cron, a Stripe webhook, a queue task), or `api` (an API key). `whoOf(ctx)` in `record.ts` is the one place that decides it. The words use the person's first name (looked up by email in `person`), "the customer", or "Trailhead" for system and api. `who` of a backfilled row: `public:*` is `customer`, `api-key:system` is `system`, any other `api-key:*` is `api`.
3. **One vocabulary, dotted.** Kinds are `record.verb`, the webhook names where one exists (`visit.scheduled`, `visit.moved`, `visit.done`, `pass.cancelled`, `payment.succeeded`, `payment.refunded`, `invoice.sent`, `invoice.reminded`) and the same style for the rest. The old `pass_change` kinds are translated once, by one map (`LEGACY_EVENT_KIND` in `src/lib/events/kinds.ts`), used by `recordChange` and mirrored by the migration's `case` (a test asserts they agree). A new kind that is not in `EVENTS` in `src/api/v1/webhooks/deliver.ts` is recorded only, never delivered: adding outbound names is a separate decision.
4. **Notes are events** of kind `note` (`detail.text`, up to 2000 characters), about a customer, property, job or visit. The `visit.notes` and `job.notes` columns are written as aliases (the newest note's text) when a note is added about that record, and are dropped in step 6. `property.notes` is a standing fact about the yard, edited in the Property block, not a log: it stays as it is, an edit of it is a `property.edited` event, and a note added about a property does not overwrite it. The backfill still makes one `note` event from each non-empty `visit.notes`, `job.notes` and `property.notes`, so nothing a person typed disappears from the story. The backfilled note's `at` is the row's `updated_at`, so it can sit later than the day it was typed.
5. **Who may add a note.** A tech sees the story and can add a note, but a tech has only the `read` scope. `events.note` therefore has scope `read` and refuses a read-only API key (`principal.kind` is not a signed-in person and no `write` scope: "A read key cannot add notes"). Verify the principal's shape in `src/lib/auth/types.ts` and `principal.ts` before writing the check. A tech never sees money, card, consent or contact events (decision 6).
6. **What a tech reads.** Without the `write` scope, `events.list`, `customers.get` and `VisitOut` return only kinds `note`, `job.sold`, `pass.*`, `visit.*`, and strip `amount`, `price`, `total`, `reference`, `gateCode`, `accessNote`, `contactPhone`, `email`, `phone` from `detail` (`techEvent(event)` in `src/lib/events/words.ts`, tested). `payment.*`, `invoice.*`, `card.*`, `consent`, `customer.edited` and `property.edited` are dropped.
7. **Staff only.** Events and notes are never on the customer's pass page, in a message, or through any customer-scoped call (`customerSelf` handlers never touch `event`). The brief's "pass page history" does not exist today (nothing on the pass page reads `pass_change` for display); the pass page's two internal readers, the consent snapshot and the day-filled line in the purchase confirmation, move to events.
8. **The admin loads events like messages.** `src/lib/admin/live.ts` loads the organization's newest 5,000 events once (`all()` pattern as messages) and the shaping groups them by customer, job and visit; `customers.get` carries the customer's last 50 and `VisitOut` the visit's last 50. The panels add a note through a server action that calls `events.note` and reloads.
9. **The purge.** `expirePendingPasses` (`src/lib/pass/server/create.ts` ~102) already deletes a never-paid pending pass and its rows; it also deletes the `event` rows whose `job_id` is one of those jobs (they record a checkout that never finished, not history).
10. **Messages in the story.** The Notes and history block shows messages beside events: `message_log` rows of the customer (or of the visit) become one line each, "Text sent: day-before reminder", never the body (the existing Messages block keeps the bodies). The merge is `timelineOf(events, messages)` in `src/lib/events/timeline.ts`, pure and tested; nothing is copied into `event`.
11. **Names in the sentence.** Events are history, so each carries what it needs to read on its own: visit, payment and invoice events put `name` ("Spring turn-on", the line name from `LINE_NAMES`) in `detail`; the words say "the visit" when it is missing.

**The backfill (appended to 0020 after the generated DDL, every statement `on conflict (id) do nothing`)**

```sql
insert into event (id, organization_id, about, about_id, customer_id, job_id, visit_id, kind, detail, who, at, created_at, updated_at)
select 'evt_pc_' || pc.id, pc.organization_id, <about>, <about_id>, pc.customer_id, <job_id>, pc.visit_id, <mapped kind>, pc.detail, pc.by_principal, pc.at, pc.created_at, pc.updated_at
from pass_change pc
left join visit v on v.id = pc.visit_id
left join season_pass sp on sp.id = pc.pass_id
on conflict (id) do nothing;
```

`<mapped kind>` is `case pc.kind when 'consent-snapshot' then 'consent' ... else pc.kind end` for the table's legacy kinds; `<about>` is `visit` when `pc.visit_id` is set and the mapped kind starts with `visit.`, else `job` when `coalesce(sp.job_id, v.job_id)` is set, else `customer`; `<about_id>` and `<job_id>` follow (`coalesce(sp.job_id, v.job_id)`). Then one insert per notes column: `visit.notes` (about visit, job from `v.job_id`), `job.notes` (about job), `property.notes` (about property, customer from `property.customer_id`), each where `notes is not null and trim(notes) <> ''`, kind `note`, `detail = jsonb_build_object('text', notes)`, `who` `system`, `at` the row's `updated_at`. No rows are deleted and no column is dropped.
